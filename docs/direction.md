## 1. 背景・目的

baserCMS 5 には管理画面のデータメンテナンスに手動のDBバックアップ機能があるが、以下の要望を満たす仕組みがない。

- CLI・cron による**定期自動バックアップ**
- アップロードファイル（files）を含む**フルバックアップ**
- 保存先フォルダの指定・**世代管理（ローテーション）**
- 将来的な**外部ストレージ（S3 / Google Drive 等）への自動転送**

BcBackup は「管理画面でプラグインを有効化すると、GUI からも CLI からもバックアップできる」ことをゴールとするプラグインである。

- 🔵 [確定] GUI（管理画面）と CLI の両対応とする
- 🔵 [確定] 定期実行は OS の cron から CLI コマンドを叩く方式とする（コアにスケジューラ・キュー機構が存在しないため。7章参照）

## 2. 前提: コア既存機能の調査結果

**ゼロから作らず、コアの `BcDatabaseService` / `UtilitiesService` の API を再利用する**ことを基本方針とする。調査で確認できた再利用可能な API は以下のとおり。

| API | 場所 | できること |
|---|---|---|
| `UtilitiesService::backupDb()` | `plugins/baser-core/src/Service/UtilitiesService.php:302` | 全プラグインのテーブルをスキーマPHP＋CSVで `TMP/schema/` に出力し ZIP 化 |
| `UtilitiesService::restoreDb()` | 同 `:396` | アップロードZIPを展開し、トランザクション内で drop→create→CSV投入（※`$_FILES` 前提のため CLI からは再利用不可 → 8章） |
| `BcZip::create()` / `extract()` | `plugins/baser-core/src/Utility/BcZip.php:362` / `:68` | ZIP の生成・展開（展開側は zip-slip 対策済み。生成側は除外パターン・エラー処理なし → 9章） |
| `BcDatabaseService::writeSchema()` | `plugins/baser-core/src/Service/BcDatabaseService.php:1034` | テーブル単位のスキーマPHP生成 |
| `BcDatabaseService::writeCsv()` | 同 `:765` | テーブル内容のCSV出力（MySQL/PostgreSQL/SQLite のドライバ差異吸収済み） |
| `BcDatabaseService::loadSchema()` / `loadCsv()` | 同 `:1215` / `:445` | リストア側の対 |
| `BcDatabaseService::updateSequence()` | 同 `:670` | リストア後のシーケンス更新（PostgreSQL対応） |
| `BcUtil::getCurrentDbConfig()` | `plugins/baser-core/src/Utility/BcUtil.php:465` | 現在のDB接続設定（driver / host / database / prefix 等）の取得 |

- 🔵 [確定] コアの ZIP バックアップ（スキーマPHP＋CSV）が、baserCMS 4 の「cakeSchema で保存」に相当する 5 系の仕組みである
- 🔵 [確定] プラグイン実装の参考構成は `plugins/CuStatic`（Command + Service 委譲 + `config/setting.php` の adminNavigation + 自己完結 `templates/Admin`）

## 3. DBバックアップ方式（RDB別）

### 方針: 2段構え

- 🔵 [確定] **標準方式**: コアAPI（スキーマPHP＋CSV）によるエクスポート
  - 長所: 外部コマンド不要／MySQL・PostgreSQL・SQLite すべて同一コードで対応／`exec()` が禁止された共用サーバでも動作／リストアもコアAPIで完結
  - 短所: 大量データではネイティブツールより遅く、PHP のメモリ・実行時間制限の影響を受ける
- 🔵 [確定] **オプション方式**: ネイティブツールによるダンプ（利用可能な環境でのみ選択可）
  - MySQL: `mysqldump`
  - PostgreSQL: `pg_dump`
  - SQLite: DBファイルのコピー（`ROOT/db/sqlite/` 配下。ファイルコピー前に整合性確保が必要 → 9章）

### オプション方式の実装要件

- 🔵 [確定] `exec()`（または `proc_open()`）の利用可否とコマンドの存在を自動検出し、使えない場合は標準方式へフォールバックする
- 🔵 [確定] 認証情報をコマンドライン引数に載せない（`ps` で漏洩するため）
  - mysqldump: 一時ファイルに認証情報を書いて `--defaults-extra-file` で渡す（実行後即削除・パーミッション 600）
  - pg_dump: 環境変数 `PGPASSWORD` または `PGPASSFILE` で渡す
- 🔵 [確定] コマンドパス（`/usr/bin/mysqldump` 等）は**管理画面の設定画面で指定可能**とする。自動検出した結果を初期値として提示する
    

## 4. バックアップ範囲

### フルバックアップ（v1）

- 🔵 [確定] 対象は **DB全体 ＋ アップロードファイル**
- 🔵 [確定] バックアップ対象ディレクトリは**管理画面の設定画面で指定可能**とする
  - デフォルト（標準）: `webroot/files/`
  - プリセットとして **`webroot` 全体**も選択可能とする（テーマ・プラグインが `webroot` 直下に書き込むケースに対応）
  - 任意ディレクトリの追加指定も可能とする（例: 独自プラグインの設定ファイル、`config/` 配下）
- 🔵 [確定] **コア・プラグインのファイルはデフォルト対象外**とする。理由: Git 管理または再インストールで復元可能であり、バックアップ容量・時間を大きく増やすため（必要なら上記の任意ディレクトリ指定でカバー）


### 差分バックアップ（v1）

- 🔵 [確定] **files は差分バックアップ対象、DB は毎回フル**とする
  - files: 前回バックアップ時点のファイル一覧（パス＋更新日時＋サイズ、必要ならハッシュ）をマニフェストとして保存し、変更・追加ファイルのみアーカイブする
  - DB: 真の差分バックアップには binlog（MySQL）/ WAL（PostgreSQL）の管理が必要で、共用サーバでは権限的にも非現実的。DBは通常サイトでは files より小さいため毎回フルで十分と判断
- 🔵 [確定] 差分の検知方式は2モードとし、設定画面で選択可能とする
  - デフォルト: **速度重視モード**（更新日時＋サイズの比較）
  - オプション: **厳格モード**（ハッシュ比較まで行う。確実だが大量ファイルでは遅い）
- 🔵 [確定] リストア時の差分適用順序（フル＋差分チェーンの復元手順）は下記の設計案で確定（2026-07-11 レビュー）

#### 差分チェーン管理の設計（2026-07-11 確定）

- 🔵 [確定] **チェーンID＋連番方式**とする
  - フルバックアップ実行時に、そのタイムスタンプを**チェーンID**とする（例: `20260712_020000`）
  - 以降の差分は「親チェーンID＋連番」を持つ。ファイル名にも埋め込む

```
backup/
  20260712_020000_full.zip           # チェーンの起点（フル）
  20260713_030000_diff_20260712_020000_001.zip   # 同チェーンの差分 #1
  20260714_030000_diff_20260712_020000_002.zip   # 同チェーンの差分 #2
  catalog.json                       # 保存先ルートの管理台帳
```

  - 各ZIP内に `manifest.json` を同梱する（種別（full/diff）、チェーンID、連番、対象ディレクトリ、ファイル一覧（パス・更新日時・サイズ・ハッシュ）、削除されたファイルの一覧、baserCMS/プラグインのバージョン）
  - **リストア手順**: チェーンのフルを展開 → 連番順に差分を上書き展開 → 各差分の削除ファイル一覧を適用
- 🔵 [確定] **管理情報（世代管理の台帳）は DB に持たせず、保存先内の `catalog.json`＋各 `manifest.json` を正とする**。理由: DBリストアを行うと DB 上の管理情報自体が過去に巻き戻り、実ファイルと不整合になるため。GUI の一覧表示は保存先ディレクトリのスキャン（catalog.json 参照）で構築する
- 🔵 [確定] ローテーションは**チェーン単位**で行う（6章参照）。フルだけ消して差分が孤児になる事故を構造的に防げる

## 5. 保存先

### v1: サーバ上の指定フォルダ

- 🔵 [確定] 保存先フォルダは**管理画面の設定画面で指定可能**とする
- 🔵 [確定] **デフォルトは webroot 外**（例: `ROOT/backup/`）とする
- 🔵 [確定] ただし、**ドキュメントルート配下しかアクセスできない FTP アカウント運用のサーバがある**ため、webroot 配下の指定も許容する。その場合は以下の保護を必須とする
  - `.htaccess`（`Require all denied`）の自動設置による直アクセス遮断
  - 保護が効かない環境（nginx 等 .htaccess 無効）向けに、設定画面で警告を表示する
- 🔵 [確定] バックアップファイルには全個人情報が含まれるため、Web から取得可能な場所への平置きは絶対に避ける（上記保護なしでの webroot 配下保存は不可）

### 将来: 外部ストレージ転送（v2以降）

- 🔴 [未定] S3 / Google Drive / SFTP（別サーバ）への自動アップロード
  - 現状 `league/flysystem` / `aws/aws-sdk-php` 等は未導入のため、**追加の composer 依存が必要**
  - flysystem を抽象化レイヤーとして採用すれば S3・SFTP・Google Drive をアダプタ差し替えで対応できる
  - Google Drive は OAuth 同意・トークン更新の運用コストが高く、優先度は S3（S3互換含む）→ SFTP → Google Drive の順を想定
- 🔵 [確定] v1 では「保存先ディレクトリを NFS / マウント済みストレージにすれば実質別サーバ保存が可能」という運用回避策をドキュメントに明記する

## 6. 世代管理・ローテーション（v1）

- 🔵 [確定] 保持数を設定し、バックアップ成功時に古いものから自動削除する
- 🔵 [確定] 保持単位は**「世代数」「保持日数」の両方をサポート**する（設定画面でどちらか、または併用を選択。併用時は先に達した条件で削除）
- 🔵 [確定] 差分バックアップとの整合: フルを消すとそこに連なる差分が復元不能になるため、**チェーン単位（フル＋連なる差分をひとまとまり）でローテーションする**（4章の「差分チェーン管理の設計」参照）。保持世代数の数え方は「チェーン数」とする（2026-07-11 確定）

## 7. 実行方式

### GUI（管理画面）

- 🔵 [確定] CuStatic の構成を踏襲し、以下を提供する
  - 設定画面 — `config/setting.php` の adminNavigation に登録。設定項目: 保存先フォルダ／DBバックアップ方式（標準・ネイティブ）／ネイティブコマンドパス／バックアップ対象ディレクトリ（デフォルト `webroot/files/`、`webroot` 全体プリセット、任意追加）／差分検知モード（速度重視・厳格）／保持世代数・保持日数／メンテナンスモード連携の ON/OFF
  - 手動バックアップ実行
  - バックアップ一覧（取得日時・種別（フル/差分）・サイズ）＋ ダウンロード・削除
  - crontab 記述例の表示（cron 設定支援。下記「定期実行」参照）
- 🔵 [確定] **タイムアウト対策を v1 で実装する**。GUI からの実行は PHP の実行時間制限を受けるため:
  - GUI では警告を表示し、大規模サイトには CLI（cron）を案内する
  - GUI 実行は**非同期実行**とする。実装案: バックグラウンドで CLI コマンドを起動し、進捗をログファイル経由で管理画面にポーリング表示する（CuStatic で実績のあるリアルタイムログ表示パターンを踏襲）
  - 🔵 [確定] `exec()` が使えない環境では **GUI 実行不可とし、CLI（cron）の案内のみ**とする（同期実行フォールバックは実装しない。2026-07-11 確定）

### CLI

- 🔵 [確定] CakePHP Command として実装し、Service へ委譲する（CuStatic の `defaultName()` パターン）

```
bin/cake bc_backup run --full          # フルバックアップ
bin/cake bc_backup run --diff          # 差分バックアップ（filesのみ差分、DBはフル）
bin/cake bc_backup list                # バックアップ一覧
bin/cake bc_backup restore <name>      # リストア
```

- 🔵 [確定] サブコマンド体系は上記のとおりとする（`run --full` / `run --diff` / `list` / `restore <name>`。restore も CLI に含める）

### 定期実行（cron）

- 🔵 [確定] コアにスケジューラ・キュー機構がないため、OS の crontab から CLI を実行する方式とする。README に記述例を載せる

```cron
# 毎日 3:00 に差分、毎週日曜 2:00 にフル
0 3 * * 1-6 cd /path/to/app && bin/cake bc_backup run --diff >> /var/log/bc_backup.log 2>&1
0 2 * * 0   cd /path/to/app && bin/cake bc_backup run --full >> /var/log/bc_backup.log 2>&1
```

- 🔵 [確定] 管理画面の cron 設定支援は **crontab 記述例の表示のみ**とする（設定内容に応じたコマンド例を管理画面に表示。crontab の自動書き換えは行わない）

## 8. リストア

- 🔵 [確定] DBリストアは v1 に含める。コアの `loadSchema()` + `loadCsv()` + `updateSequence()` を再利用すれば実装コストは小さい
- 🔵 [確定] ただし、コアの `UtilitiesService::restoreDb()` は**そのままでは再利用できない**（2026-07-11 調査で確認）。`$_FILES['backup']` のアップロードファイル前提の実装（`UtilitiesService.php:415`）のため、CLI・保存済みファイルからのリストアには使えない。BcBackup 側で `BcZip::extract()` → `loadSchema()` / `loadCsv()` → `updateSequence()` を組み合わせた独自リストア処理を実装する（コアの `_loadBackup()` 相当のロジックを参考にする）
- 🔵 [確定] files のリストア（フル＋差分チェーンの展開）は **v1 では CLI（`restore <name>`）のみサポートし、GUI は手動展開手順のドキュメント提供とする**（2026-07-11 確定）。GUI からの files リストア実行は将来対応
- 🔵 [確定] ネイティブダンプ（mysqldump 等）で取得したバックアップのリストアは、**手動リストア（`mysql < dump.sql` 等）の手順書（ヘルプ）提供のみ**とする。GUI/CLI でのリストア実行はサポートしない（2026-07-11 確定）。このため pg_dump はリストア手順を `psql` で完結できる**プレーン SQL 形式（`-Fp`）**で取得する

## 9. 懸念点・検討事項

1. 🔵 [確定] **PHP 実行時間・メモリ制限**: 大容量サイトでは GUI 実行がタイムアウトしうる。CLI を正とし、GUI は警告表示＋非同期実行を v1 で実装する（7章参照）
2. 🔵 [確定] **バックアップ中の整合性 — メンテナンスモード連携は技術的に可能**。コアにはメンテナンスモードが実装済み: サイト基本設定 `BcSiteConfig::get('maintenance')` が ON のとき、フロントは `/maintenance` へリダイレクトされる（`plugins/baser-core/src/Controller/AppController.php:332` `redirectIfIsRequireMaintenance()`）。バックアップ開始時に `site_configs` の `maintenance` を ON、完了時に OFF へ更新すれば自動切替できる。実装上の注意:
   - 途中でクラッシュしても解除されるよう try/finally で確実に元へ戻す（元の設定値を退避し、元々メンテナンス中だったサイトを誤って公開しない）
   - メンテナンスモードは管理画面・管理者ログイン中・debug モードでは効かない仕様のため、完全な書き込み停止ではない（管理者操作は止まらない）点をドキュメントに明記
   - 🔵 [確定] 自動メンテナンスモードは**デフォルト ON（設定で変更可）**とする。加えてネイティブ方式では `mysqldump --single-transaction` 等で DB 単体の整合も既定で確保する（これも設定で変更可）（2026-07-11 確定）
   - 🔵 [確定] `--single-transaction` が整合を保証するのは **InnoDB のみ**（MyISAM テーブル混在時は保証されない）。メンテナンスモード併用がその保険となる点をドキュメントに明記する
3. 🔵 [確定] **バックアップファイル自体が個人情報の塊**: 保存先保護（5章）、管理画面ダウンロードの権限制御は必須。暗号化（ZIP パスワード / GPG）は将来検討（🔴 [未定]）
4. 🔵 [確定] **`exec()` 無効・ネイティブツール不在環境**: 標準方式（コアAPI）があるため致命的でない。自動フォールバックで対応
5. 🔵 [確定] **RDB別の動作検証**: 本 Docker 環境には MySQL 8.0 / PostgreSQL 15.2 が定義済み。SQLite 含め**3種での検証をリリース条件とする**（2026-07-11 確定）
6. 🔵 [確定] **失敗時の通知**: ログ（CakeLog）への出力を必須とする。加えて実行形態別に:
   - GUI: 画面に成否・エラー内容を表示（非同期実行時はポーリングで結果反映）
   - CLI: 結果を echo、エラーは **stderr** に出力し、終了コードを非0にする（cron の `MAILTO` によるメール通知がそのまま機能する）
   - プラグイン独自のメール送信機能は v1 では持たない（cron のメール通知に委ねる）。将来検討
7. 🔵 [確定] **SQLite のファイルコピー整合性**: 稼働中の単純コピーは破損リスクがあるため、**メンテナンスモード（上記2）＋ `VACUUM INTO`** を第一候補とする（SQLite 3.27+）。旧 SQLite 環境向けフォールバックは **`VACUUM INTO` → PHP `SQLite3::backup()` → 標準方式（コアAPI）の自動フォールバック順**とする（2026-07-11 調査で確定。根拠: `ext-sqlite3` はルート `composer.json:13` の必須依存であり利用を前提にでき、`SQLite3::backup()` の基盤である SQLite Online Backup API は 3.6.11+ で利用可能なため、実質すべての環境をカバーできる）
8. 🔵 [確定] **リストアの安全装置**: リストア直前の自動バックアップは実装しない。代わりに、リストア実行時に**「バックアップを取ってから実行する」ことを促す確認メッセージのみ**とする（GUI は確認ダイアログ、CLI は確認プロンプト。2026-07-11 確定）
9. 🔵 [確定] **排他制御（多重実行防止）が必須**（2026-07-11 調査で追加）: コアに汎用ロック機構は存在しない（`flock` 利用箇所なし）。さらに `UtilitiesService::backupDb()` は共有の `TMP/schema/` を実行前後で空にするため、cron の重複起動・GUI と cron の同時実行・コア標準の手動バックアップとの並走で衝突する。**ロックファイル（`flock`）による多重実行防止を v1 で実装**し、ロック取得失敗時はエラー終了（CLI は非0終了）とする
10. 🔵 [確定] **ZIP 生成の原子性と自己包含防止**（2026-07-11 調査で追加）:
   - 書き込み途中のファイルが完成品として扱われないよう、**一時名（`.tmp` 等）で生成し完成後に rename** する。`catalog.json` の更新も同様（テンポラリ書き込み→rename）。起動時に残骸の `.tmp` を掃除する
   - 保存先ディレクトリがバックアップ対象ディレクトリの配下にある場合（例: 対象 `webroot` 全体＋保存先 `webroot/backup/`）、**保存先自身を対象から除外**しないと自己包含で肥大化する。除外処理を必須とする
   - コアの `BcZip::create()` は除外パターン・エラー処理・戻り値を持たないため、**files のアーカイブ処理は BcBackup 側で独自実装**する（`ZipArchive` 直接利用。`ext-zip` はルート `composer.json:14` の必須依存のため前提にできる。ZIP 展開はコアの `BcZip::extract()`（zip-slip 対策済み）を再利用）
11. 🔵 [確定] **ディスク空き容量チェック**（2026-07-11 調査で追加）: バックアップ開始前に `disk_free_space()` で保存先の空き容量を確認し、推定サイズ（前回実績 or 対象サイズ合計）を下回る場合は実行せずエラーとする
12. 🟡 [要確認] **ネイティブコマンドの互換性差異**（2026-07-11 調査で追加。実装時に検証）:
   - MariaDB 環境ではコマンド名が `mariadb-dump`（旧 `mysqldump` はシンボリックリンク）。自動検出は両方を探す
   - MySQL 8 系ではクライアント／サーバのバージョン不一致時に `column-statistics` エラーが発生する既知問題があり、オプション付与での回避を検証する
   - GTID 有効環境の mysqldump は `--set-gtid-purged=OFF` がないと復元先を選ぶダンプになる
13. 🔵 [確定] **リストア時もメンテナンスモード連携を行う**（2026-07-11 調査で追加）: リストア中のサイトは不整合状態でありバックアップ時以上に危険なため、上記2と同じ仕組み（try/finally で復帰）を DB リストアにも適用する

### 決定済み（2026-07-11 レビューで確定）

- 差分チェーン管理の設計（チェーンID＋連番、catalog.json / manifest.json 正、チェーン単位ローテーション、リストア手順）は設計案どおりで確定（4章・6章）
- files リストアは v1 では CLI（`restore <name>`）のみサポート。GUI は手動展開手順のドキュメント提供とし、GUI 実行は将来対応（8章）
- リストアの安全装置は、自動バックアップではなく「バックアップを取ってから実行する」ことを促す確認メッセージのみとする（9章-8）
- `exec()` が使えない環境の GUI 実行は、フォールバック実装なし・CLI 案内のみ（7章）
- ネイティブダンプのリストアは手動リストア手順書（ヘルプ）の提供のみ。pg_dump はプレーン SQL 形式で取得（8章）
- 自動メンテナンスモードはデフォルト ON（設定で変更可）。ネイティブ方式では `--single-transaction` 等の DB 単体整合も既定で確保（設定で変更可）（9章-2）
- RDB 3種（MySQL / PostgreSQL / SQLite）での動作検証をリリース条件とする（9章-5）

### 追加調査で確定（2026-07-11 コード調査）

- コアの `restoreDb()` は `$_FILES` 前提のため再利用不可。BcBackup 独自リストアを `loadSchema()` / `loadCsv()` / `updateSequence()` で実装（2章・8章）
- 旧 SQLite フォールバックは `VACUUM INTO` → `SQLite3::backup()` → 標準方式の自動フォールバック順（`ext-sqlite3` はコア必須依存）（9章-7）
- 排他制御（flock ロックファイル）を v1 必須とする。コアにロック機構なし・`TMP/schema/` 共有のため（9章-9）
- ZIP は一時名生成→rename の原子的書き込み、保存先の自己包含除外、files アーカイブは独自実装（`BcZip::create()` は除外・エラー処理なし）（9章-10）
- 実行前のディスク空き容量チェック（9章-11）
- リストア時もメンテナンスモード連携を行う（9章-13）
- 追加の composer 依存なしで v1 実装可能（`ext-zip` / `ext-sqlite3` はルート composer.json の必須依存）

### 決定済み（2026-07-10 レビューで確定）

- ネイティブコマンドパスは設定画面で指定可能（自動検出値を初期値に）（3章）
- バックアップ対象ディレクトリは設定画面で指定可能。デフォルト `webroot/files/`、`webroot` 全体プリセット、任意追加可（4章）
- 差分検知はデフォルト速度重視モード（更新日時＋サイズ）、オプションで厳格モード（ハッシュ）（4章）
- 保存先はデフォルト webroot 外。ドキュメントルート配下しかアクセスできない FTP アカウント環境向けに webroot 配下も指定可（保護必須）（5章）
